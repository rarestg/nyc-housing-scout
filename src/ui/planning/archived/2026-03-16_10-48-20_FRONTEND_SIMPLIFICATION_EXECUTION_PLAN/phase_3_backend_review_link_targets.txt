Phase 3 Task: Backend Review Link Targets
=========================================

Mission
-------
Move review-link semantics into the backend read model so frontend routes stop re-deriving them. Add a canonical review navigation field to the relevant listing payloads and consume it in the frontend. Delete the existing frontend heuristics.

Dispatch order
--------------
- third phase
- depends on the route simplification phases being stable enough to consume the new payloads cleanly

Core deliverables
-----------------
1. Pick one canonical backend field for review navigation.
2. Expose that field on listing list/detail payloads where review navigation is needed.
3. Expose that field on linked-listing payloads used by Posts detail.
4. Consume the backend field in Listings and Posts.
5. Delete frontend helpers that currently derive review IDs or queues from listing fields.
6. Add test coverage for the new contract.

Requirements
------------
- Keep the contract read-only and lightweight.
- Do not duplicate queue-threshold logic in both backend and frontend.
- Choose a field name that reads as canonical intent, not an implementation leak.
- If the best shape is `reviewLinkTarget`, use that or a similarly explicit field.

Out of scope
------------
- changing how the Review route itself computes queue rows
- any new review queue categories
- Listings chrome cleanup

Validation
----------
- `npm test`
- verify:
  - listing detail to review navigation
  - post linked-listing to review navigation
  - no remaining route-local review derivation helpers

Success criteria
----------------
Review navigation semantics come from the backend read model, and the frontend no longer re-implements the review-routing rules.
