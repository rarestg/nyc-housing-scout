Core deliverables
-----------------
1. `Posts` route:
   - cross-group chronological feed/table
   - body preview
   - author
   - source group
   - freshness
   - processing status
   - linked listing count
   - detail pane support
2. `Review` route:
   - ambiguous items
   - low-confidence items
   - pending jobs
   - failed jobs
   - incomplete items
   - later room for duplicate-suspect queues
3. `Debug` route:
   - preserve the current run-centric inspection power
   - clearly demote it from the primary home flow
   - keep provenance, artifacts, validation, and raw payload access available
4. Replace the existing placeholder routes with route-owned modules and wire them into `DashboardApp.jsx`.

Requirements
------------
- Make it easy to move from a listing to the raw post evidence and then into debug only if needed.
- Do not let Debug reclaim visual dominance over the product.
- Keep JSON and artifacts available, but not as the primary browsing surface.
- Use the same table/list plus detail-pane philosophy where it makes sense.
- Reuse the shared shell primitives instead of rebuilding them:
  - `useDashboardShellSlots(...)`
  - `DataTable`
  - `RouteScaffold`
  - `FilterBar`, `FilterField`, `FilterInput`, `FilterSelect`
  - `useUrlQueryState`
- Consume the new paginated API envelope instead of assuming the legacy inspector `{ count, items }` shape.

Important product framing
-------------------------
The user cares most about actual listings. `Posts` exists because the raw Facebook post is still the evidence layer. `Debug` exists because provenance matters. Neither should overpower the main listings experience.
