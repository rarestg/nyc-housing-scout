Current state
-------------
Stage A and Stage B are complete.

Current product shape:
- dashboard shell at `/`
- `Listings` as the default route
- real server-backed `Posts`, `Review`, and `Debug` routes
- legacy inspector preserved at `/inspector`

Your job is to make this result tighter, cleaner, and more maintainable without changing the core product direction.

Ownership
---------
You may work across the integrated dashboard surface, including:

- `src/ui/dashboard/`
- `src/ui/inspection-server.js` if a small integration seam truly needs cleanup
- dashboard-related tests under `test/`
- minimal docs updates if commands or operator guidance changed
- a new pass doc under `docs/passes/` for this Stage C pass

You should not:
- redesign the product direction again
- introduce map view
- introduce push notifications
- add auth
- redesign storage schema unless absolutely necessary
- build backend duplicate clustering

Important scope priorities
--------------------------
1. Integration coherence
2. UX polish
3. Simplification / code reduction
4. Accessibility and responsive cleanup
5. Documentation and pass log

Known issues to address
-----------------------
1. Listings route duplicates logic that already exists in shared route support.
   - Specifically, the listings route re-implements fetch/API/pagination helpers that already exist elsewhere.
   - Consolidate this if it improves maintainability without degrading clarity.

2. Review deep links are still page-scoped.
   - Right now a `reviewId` only resolves if the item is on the current page of `items`.
   - If there is a clean way to improve this without overbuilding, do it.
   - If not, keep the behavior honest and well-signaled in the UI.

3. General polish and consistency still matter.
   - consistent loading/error/empty states
   - consistent pagination behavior
   - consistent detail-pane behavior
   - truncation/overflow/wrapping cleanup
   - focus states and keyboard behavior
   - consistency across Listings, Posts, Review, and Debug

4. Simplification is explicitly in scope.
   - If you can reduce line count and duplicated logic while preserving the same UX and clarity, do it.
   - Prefer fewer concepts, fewer helper variants, and less repeated fetch/query/pagination glue.
   - Do not golf the code into unreadability.

Specific simplification questions to ask yourself
-------------------------------------------------
- Can repeated route patterns be extracted cleanly?
- Can duplicated pagination or fetch helpers be unified?
- Can repeated detail-panel wiring be simplified?
- Can formatting helpers or shared state patterns remove route-specific boilerplate?
- Can old placeholder/demo remnants now be removed safely?
- Can the same UX be preserved with fewer ad hoc helper functions?

Polish expectations
-------------------
Please look across the integrated dashboard for:

- visual consistency between routes
- filter ergonomics
- detail-pane clarity
- responsive behavior at narrower widths
- text wrapping and overflow
- humanized timestamps
- raw ID demotion
- debug staying secondary
- keyboard reachability and focus visibility

You do not need to invent a new visual design language. This is about making the current direction tighter and more credible.

Success criteria
----------------
The dashboard should feel like one coherent product surface rather than four freshly landed route slices.

It should also be simpler:
- less duplicated code
- fewer route-specific one-off helpers
- clearer shared patterns
- same or better UX

If you can achieve the same UX with many fewer lines of code, do it.
