# Ingest Loop CLI Spec

Status: draft implementation spec for the next worker.

## Why this pass exists

We now have a working browser-relay ingestion path and a working Gemini queue path, but they still require a human to manually:

1. verify the attached Facebook tab
2. run a crawl
3. inspect whether the top of the feed is stale / already cached
4. refresh the page
5. rerun crawl + queue processing

This spec defines a small explicit CLI that automates that operator loop without inventing a new daemon or orchestration layer.

## Core answer to the relay question

Yes, a plain repo CLI can drive the loop.
It does **not** need an OpenClaw chat agent sitting in the middle of every cycle.

The dependency chain is:

1. the CLI/script calls the existing `openclaw browser ...` commands
2. OpenClaw browser control talks to the configured `chrome` browser profile
3. that profile points at the Chrome extension relay
4. the relay drives the explicitly attached Facebook tab

So the new loop CLI is still browser-state dependent, but it can run as a normal repo command.

## Current implementation surface to build on

Use the existing pieces rather than replacing them:

- `src/core/browser-pipeline.js`
  - already shells out to `openclaw browser ...`
  - provides `runBrowser()`, `evaluateJson()`, and banner stripping
- `src/cli/crawl-dom-latest.js`
  - current live ingestion primitive
- `src/cli/validate-queue.js`
  - current queue + Gemini validation path
- `src/cli/inspect-storage.js`
  - useful if state inspection is needed during the loop

The live-tested operator doc for expected behavior is:
- `docs/notes/2026-03-13_13-16-00_BROWSER_RELAY_INGESTION_SOP.md`

## Goal

Add a small CLI that can:
- target the attached Facebook group tab through the existing browser relay
- reset to the group URL / top-of-feed each cycle
- run a crawl
- detect whether results are fresh vs mostly already seen
- process fresh observations through the Gemini queue path
- refresh/revisit on a loop
- emit lightweight callback notifications through OpenClaw system events
- stop cleanly when asked

## Proposed CLI

Add:
- `src/cli/ingest-loop.js`

Add npm script:
- `ingest:loop`: `node src/cli/ingest-loop.js`

## Scope constraints

### In scope
- one explicit long-running CLI
- browser preflight / health checks
- deterministic refresh/reset each cycle
- crawl + queue processing orchestration
- JSON stdout summaries and a small local state file
- OpenClaw system-event callbacks
- stop file and signal handling

### Out of scope
- no new daemon
- no new scheduler
- no new orchestration layer
- no browser-driver replacement
- no UI work in this pass
- no geocoding / mapping enrichment in this pass
- no attempt to manage multiple tabs or multiple sources concurrently

## CLI contract

### Required flags

- `--source-key <key>`
- `--display-name <name>`
- `--group-url <url>`

### Optional flags

- `--browser-profile <profile>` default: `chrome`
- `--target <n>` default: `10`
  - forwarded to `crawl-dom-latest`
- `--max-scrolls <n>` default: `10`
- `--process-limit <n>` default: `10`
- `--sample-limit <n>` default: `3`
- `--poll-interval-ms <n>` default: `120000`
  - wait between healthy cycles
- `--idle-interval-ms <n>` default: `60000`
  - wait after a no-fresh / stale cycle
- `--max-cycles <n>` default: `0`
  - `0` means run until stopped
- `--max-idle-cycles <n>` default: `0`
  - `0` means unlimited
- `--state-file <path>` default: `data/state/ingest-loop/<source-key>.json`
- `--stop-file <path>` default: `data/state/ingest-loop/<source-key>.stop`
- `--log-file <path>` default: `data/state/ingest-loop/<source-key>.jsonl`
- `--notify <mode>` default: `important`
  - supported values: `off | important | verbose`
- `--skip-processing`
  - crawl only; do not run `validate:queue`
- `--dry-run`
  - run preflight + planning only; no crawl/process actions

## High-level behavior

Each loop cycle should do this:

1. check stop conditions
2. verify browser relay health
3. verify the attached tab is the intended Facebook group
4. navigate the attached tab to `--group-url`
   - this doubles as a reset-to-top refresh strategy
5. optionally wait a short settle period (for example `1500-3000ms`)
6. run `crawl-dom-latest`
7. parse crawl output JSON
8. decide whether the cycle is:
   - `fresh`
   - `idle/stale`
   - `error`
9. if fresh observations were collected:
   - run `validate:queue --freshness fresh` for that run
10. write cycle summary to stdout + JSONL log + state file
11. emit system-event callback if warranted
12. sleep the appropriate interval and repeat

## Deterministic page reset policy

This pass should **not** rely on “whatever scroll position the tab happens to be at.”

Each cycle should explicitly reset by sending the attached tab back to the group URL:

```bash
openclaw browser navigate --browser-profile <profile> <group-url>
```

Why prefer navigate over a raw reload:
- it is deterministic
- it reasserts the intended group URL
- it naturally resets top-of-feed position
- it is easier to reason about in logs

If navigate proves flaky in practice, fallback option is:
- page-context `location.reload()` via `openclaw browser evaluate`

But the first implementation should prefer `navigate`.

## Browser preflight contract

Before each cycle:

1. run browser status
2. run page-context evaluate returning at least:
   - `title`
   - `href`
3. ensure:
   - browser status is healthy
   - evaluated URL starts with `https://www.facebook.com/groups/`
   - evaluated URL matches or normalizes to the requested `--group-url`

If preflight fails:
- emit a system event
- log structured error state
- retry after `idle-interval-ms`
- do not attempt crawl/process until preflight recovers

## Cycle classification rules

### Treat a cycle as `fresh`
When:
- `crawl.summary.freshCollected > 0`

### Treat a cycle as `idle/stale`
When any of these are true:
- `freshCollected === 0`
- step log indicates top-of-feed is dominated by already seen posts
- crawl produced no meaningful additions
- scroll progression appears exhausted / flat

For the first implementation, keep the rule simple:
- `freshCollected === 0` => idle/stale

Optional richer heuristics can come later.

## Queue behavior

When the crawl yields fresh observations, the loop should process only fresh observations from that run.

Use:

```bash
npm run validate:queue -- --run-id <runId> --freshness fresh --process-limit <n> --sample-limit <n>
```

Why this path first:
- already exists
- already produces useful coverage + processing summaries
- already exercises enqueue + processing together
- already fits the repo’s current operator surfaces

Do **not** process `seen` observations by default in this loop.

## Suggested callback policy

Use `openclaw system event --text ... --mode now` for lightweight callbacks.

### `--notify important` (default)
Send callbacks only for:
- fresh posts found and processed
- browser preflight failures
- repeated idle condition hitting `max-idle-cycles`
- clean shutdown / explicit stop

### `--notify verbose`
Also send callbacks for:
- every cycle summary
- every refresh/reset action

### Example callback texts

Fresh cycle:
- `Ingest loop: 3 fresh posts captured for williamsburggreenpointhousing; 3 processed, 0 retryable, 0 failed (run 2026-03-13T17-14-28-264Z).`

Idle cycle:
- `Ingest loop: no fresh posts this cycle for williamsburggreenpointhousing; reset tab and retrying in 60s.`

Error:
- `Ingest loop: browser preflight failed for williamsburggreenpointhousing; attached tab or relay may need attention.`

```json
  "lastProcessedCount": 0,
  "lastError": null,
  "status": "running"

```

Also append per-cycle JSON lines to a log file for later debugging / UI wiring.

## Stop behavior

The CLI must stop cleanly when any of these happen:
- SIGINT / Ctrl-C
- SIGTERM
- `--max-cycles` reached
- `--max-idle-cycles` reached
- stop file exists at `--stop-file`

On clean stop:
- update state file to `status: stopped`
- emit one final callback if notifications are enabled
- do not leave ambiguous partial state

## Output contract

For each cycle, print a concise JSON object that includes at minimum:
- cycle index
- source key
- run id
- crawl outcome counts
- whether processing ran
- processing summary counts
- chosen next action (`sleep`, `retry`, `stopped`, `error`)
- next wait duration

This should be machine-friendly first, human-readable second.

## Implementation approach

Prefer a practical orchestrator inside the repo over a major refactor.

### Acceptable first implementation
A single CLI that calls existing CLIs / helpers using Node child-process execution and JSON parsing.

That is good enough for the first pass.

### Nice-to-have but not required
Factor some existing CLI logic into shared library functions if it makes the loop cleaner.
But do not make that refactor the main project of the pass.

## Known caveats the worker must preserve

- the browser relay controls only the explicitly attached tab
- Facebook login/session state still matters
- the top visible slice may under-fill on one-shot capture
- `crawl-dom-latest` is the real primitive, not `capture-dom-feed`
- this pass should not create hidden processing of `seen` observations by default
- this pass should not reintroduce lat/lng guessing into first-pass extraction

## Non-goals / what not to do

- do not add a background daemon service
- do not add cron inside the repo
- do not add a database migration for this pass unless truly necessary
- do not build UI in the same pass
- do not solve geocoding in the same pass
- do not replace `validate:queue` with a brand-new queue path unless forced

## Bottom line

The loop should be a **small explicit controller CLI** that sits on top of the already-working pieces.

That is the right level of engineering here:
- practical
- testable
- operator-friendly
- compatible with the existing OpenClaw browser relay architecture
- and not a premature platform rewrite
